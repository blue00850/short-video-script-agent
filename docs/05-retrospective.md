## 2. 最难的问题

### 2.1 “看起来通过了”不等于“真的能交付”

最早的直觉是：模型输出脚本，规则检查一下，过了就结束。真正做起来才发现有三个坑：

1. **模型会自己宣布完成**。如果 `finish` 不做门禁，模型完全可以在没 check、没 review 的情况下返回 `completed`。所以 `finish(completed)` 必须由 Agent 重新跑 `check_rules` 并检查 reviewer 结论，不能信模型的一句话。
2. **规则会漏语义**。“支持字幕”被写成“不用手动打字”，没有能力词、没有数字、没有禁用词，机械规则完全放过。必须加一个独立上下文的 reviewer，专门看“这句话是否超出 claim 的语义边界”。
3. **失败必须可解释**。6 秒目标 + 3 个镜头，单镜最短 2.0s + 转场 0.2s，理论下限 6.6s；如果只说“做不到”，用户不知道为什么。最终输出要带 `best_attempt` 和计算过程，让“失败”也是可核对的。

### 2.2 时长估算的“0.1 秒”问题

P01 首稿要求 38.0s，修正稿要求 28.0s。为了让示例与题目参考实例逐字对得上，时长不能靠四舍五入碰运气：

- 中文按 4.2 字/秒；
- 单镜先算 speech，再 `max(2.0, speech)`；
- 总时长用未取整的 speech 求和，最后统一 round 1 位；
- 转场 0.2s/镜只在总时长加，不混进 `shot_seconds`。

这带来一个测试上的坑：最初把 `shot_seconds` 当成“含转场”，期望 `[10.0, 8.8, 8.4]`，实际是 `[13.8, 12.1, 11.4]`；单镜下限测试实际 `[2.0, 2.0, 2.0]`，不是 `[2.2, ...]`。最后确认：**单镜 speech 与总时长是两个语义，测试必须分开断言**。这类“0.1 秒”的细节，如果不写测试，文档和输出很容易对不上。

### 2.3 Windows 上的临时目录

7 个 Agent 测试在 `tempfile.TemporaryDirectory()` 退出后才读 trace，Linux 上可能碰巧能读到，Windows 上目录已经删了，直接 `FileNotFoundError`。修法不是改产品，而是把读取放回 `with` 块内。这个失败提醒我：**测试代码也是代码，跨平台路径/生命周期要考虑**。

### 2.4 多 Agent 的“独立性”不是换个 prompt

一开始想的是“让同一个模型再检查一遍”。但如果 reviewer 复用 writer 的对话历史，它会被 writer 的理由带着走，变成自我确认。最终把 reviewer 做成：

- 独立上下文：只有需求、脚本、claim 目录；
- 只读：不调用 search/get，不重新写脚本；
- 输出结构化 verdict/findings；
- `severity=error` 一票否决；
- 最多 2 次，避免无限 review。

这比“多写一个 Agent 类”更有意义：**独立性是上下文边界，不是角色名字**。

## 3. 学习收获

1. **Agent 的可靠性主要来自“门禁”而不是“提示词”**。提示词可以要求“不要编造”，但只有 claim 校验、数字校验、reviewer 否决和 finish 门禁，才能让“不要编造”变成可执行的约束。
2. **确定性工具是 Agent 的锚**。时长、规则、claim 查询都应该是工具，模型负责选择和修正，不负责“感觉”。这样 Trace 才能逐项核对。
3. **失败状态是产品的一部分**。`insufficient_evidence`、`cannot_satisfy`、`step_limit_reached` 不是异常，而是对用户负责的输出；比“硬编一个 30 秒脚本”更有价值。
4. **Mock 的边界要写清楚**。Mock 能证明循环、预算、门禁、Trace，但不能证明模型决策质量；把这条写进 README 和评估文档，比假装“已用真实模型”更可信。
5. **测试会暴露文档的含糊**。`shot_seconds` 到底含不含转场、`check_rules` 的 `ok` 到底是工具成功还是检查通过，这些如果不写清楚，评审看 Trace 会误解。

## 4. 如果重做，会改什么

1. **先写 acceptance matrix，再写代码**。这次是先实现再补文档，导致 `shot_seconds` 语义、`check_rules` 的 `ok` 含义要回头解释；下次先把“每个验收点对应哪个字段/哪条 trace”列出来。
2. **真实模型优先跑一条最小路径**。Mock 很快，但真实模型的 JSON 稳定性、是否会主动压缩、是否会漏 claim，才是最大不确定性；应该在第一天就用真实 key 跑 normal，再决定 prompt 和修复策略。
3. **规则错误去重**。首版“效率提升80%”同时命中 phrase 和 regex，报了 3 次；虽然已去重，但这类“同一事实多条错误”会干扰模型修正，应该一开始就按归一化文本聚合。
4. **加一个轻量的人工评分表**。当前只验证事实/时长/结构，脚本“好不好看”没有量化；至少可以加“开头 3 秒是否有钩子”“口播是否顺口”的人工 1–5 分，但这需要真人，不应由 AI 编造。

## 5. 下一步

按优先级：

1. **真实模型验证（最高）**：拿到 `LLM_API_KEY` 后跑 normal + p01_30s，记录真实 trace；重点看模型是否在 38s 后主动压缩、是否会跳过 `get_material`、JSON 是否稳定。
2. **人工可读性评估**：找 2–3 位创作者盲评 5 条脚本，记录“是否愿意直接拍”“哪句最假”，形成小样本反馈；没有数据就不写效果百分比。
3. **素材检索增强**：当前是关键词命中，真实素材库需要向量召回/别名/同义词；但要保留 claim 级溯源，不能只召回一段文本。
4. **更丰富的失败注入**：超时、429、空 content、非法 JSON、claim 不存在，形成故障矩阵；当前只覆盖了 timeout 和连续错误。
5. **UI（可选）**：单页 Trace 查看器，把 step/action/observation/review 可视化；不做完整产品后台。

## 6. 一句话总结

这个项目最难的不是“让模型写一条脚本”，而是**让模型在工具说“不”的时候真的改，改完还能被逐项核对；改不动时，明确告诉用户为什么**。Mock 把这条链路的骨架跑通了，真实模型的效果还需要用 key 和人工评估去补，不能提前宣称。
